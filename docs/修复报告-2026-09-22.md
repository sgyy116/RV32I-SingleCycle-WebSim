## 1. 后端真 bug

### 1.1 AUIPC 的结果等于 `pc`，立即数被整个丢掉 ★最严重

**症状**：`auipc a0, 0x12345` 应当得到 `pc + 0x12345000`，实际得到 `pc`。

**证据链**（三处叠在一起才成立）：

```cpp
// rv_core.cpp:286-288
u32 op1 = out.ctrl.is_lui ? (u32)d.imm : rs1_val;
if (out.ctrl.is_auipc) op1 = m_pc;                        // op1 ← pc
u32 alu_in2 = out.ctrl.alu_src ? (u32)d.imm : rs2_val;    // op2 ← 立即数

// rv_control.hpp:51（改之前）
c.alu_op = AluOp::PASS_A;                                 // 只透传 op1
// rv_alu.hpp:28 → PASS_A: result = a;                    // op2 被丢弃
```

**`imm` 算出来又被扔掉。** 而 `rv_control.hpp:13` 当时的注释写着
「`is_auipc`: AUIPC（写回 pc+imm，ALU 用 PASS_A 直接透传）」——**注释与实现直接矛盾**，
`PASS_A` 做不了加法。对照 LUI（`:41-46`）就能看出设计意图：LUI 经 `muxa0` 把 imm 送到 op1，
`PASS_A` 透传得 imm，是对的；AUIPC 经 `muxa` 选 pc，`PASS_A` 透传得 pc，imm 就没了。

**为什么长期没被发现**（这是本次审计最值钱的一条经验）：

1. `test_basic.s:21` 当时写的正是 `auipc s5, 0` —— **imm = 0 时，错误实现与正确实现结果相同**；
2. `test_sim.py:113-125` 的期望值是从自己的 trace 里反查的（`auipc_pc = st["state"]["pc"]`），
   **断言在自证**。

**错误实现 + 恒真断言可以长期共存**，这就是标本。

**修法**（一行）：`rv_control.hpp:51` 改 `AluOp::ADD`。改完 op1 = pc、op2 = imm、ALU 做 ADD，
正好 `pc + imm`。**几何与前端一个字都不用动**——`w_ctl_aluop` 的 value 是
`s.control_signals.alu_op`，`InstructionPanel.vue:125` 同样直接读后端字段，不硬编码。

**复验**：
- `test_basic.s:21` 改成 `auipc s5, 0x12345`，`test_sim.py:137` 的期望值**由 Python 独立算**
  （`auipc_pc + (0x12345 << 12)`），不再从 trace 反查；
- `difftest/corpus.py:146` 的 `c_lui_auipc` 用非零立即数，还刻意连放两条，
  抓「imm 被丢掉」的退化形态。

### 1.2 CSR 指令真的改了寄存器，图上「寄存器写使能」却灭着

**症状**：`csrrw x1, mstatus, x2` 真的写了 x1，但数据通路图上 `regfile.wen` 与写地址线不亮。

**证据**：

```cpp
// rv_core.cpp:416-420（CSR 分支里自己写寄存器）
out.wb.source = "CSR";  out.wb.active = d.rd != 0;
if (d.rd != 0) m_regfile.write(d.rd, old);
// rv_control.hpp 的 case OP_SYSTEM: break;   ← reg_write 保持 false
// datapathHighlight.ts 的 w_dec_wen / w_dec_waddr 读的正是 control_signals.reg_write
```

学生看到的电路与 CPU 的实际动作不一致——这属于「信号传递正确」，不是观感取舍。

**修法**：CSR 分支里补 `out.ctrl.reg_write = (d.rd != 0);`（`rv_core.cpp:421-424`）。
前端一个字不用改，且 `datapathHighlight.ts` 里手抄的那张 CSR 写使能表可以退化成
`reg_write` 一条判据（第 7 节）。

**复验**：`tools/_hl_check.mjs` 的 CSR 组现在断言 `wire:w_dec_wen` / `w_dec_waddr` 必须亮；
`difftest/refmodel.py:543` 对全部语料逐周期比对 `control_signals.reg_write`。

### 1.3 `taken` 单元只建模了 BEQ —— 图上对另外五条分支是结构性错误

**症状**：图上 `taken` 是个只有 `branch` / `zf` 两个输入的 circle。`bne`/`blt`/`bge`/`bltu`/`bgeu`
照这张图**学不到它是怎么判的**，而且判据本身也不成立。

**先证明「小改不可能」**：没有任何二元 ALU 运算的零标志能表示「不相等」，所以只要
`alu_op` 按 funct3 分派，零标志最多只能编码 BEQ/BNE 这一对且极性固定。要覆盖六条分支，
图上必须多出两条输入线和一个 ALU 输出。

**最终编码**（图与实现一一对应）：

```
base  = funct3[2] ? alu.less : alu.zero        // f3[2] 在「小于」与「相等」之间选一路
taken = funct3[0] ? !base : base               // f3[0] 选极性
```

`funct3[1]` **不参与** taken —— 它决定后端在 `SLT` / `SLTU` 之间选哪个 `alu_op`，
有符号/无符号的差别就落在那里。

| 层 | 改动 |
|---|---|
| 后端 | `rv_alu.hpp` 新增 `less` 标志（`result & 1`）；`rv_control.hpp` 的 `OP_BRANCH` 按 funct3 选 `SUB`/`SLT`/`SLTU`；`rv_core.cpp:305-315` 用两个标志位 + funct3 组出 taken，删掉原来那张 `switch (d.kind)` 表；JSON 增发 `alu.less` |
| 几何 | `taken` 由 circle 改 rect（circle 的上下端口被 `check_layout.py` 强制在 `w/2` 处，放不下 5 个输入）；新增 3 条线、6 个端口 |
| 语义 | `datapathHighlight.ts` 新增 `f3bit()`；`w_alu_zf` 收紧为 `branch && !f3[2]`；新增 `w_alu_lt` ⟺ `branch && f3[2]` |

**复验**：`tools/_hl_branch.s`（新夹具）对六条分支各给一正一反两组操作数
（`x3 = -1`，有符号看是 −1、无符号看是 4294967295，正好把 `blt` 与 `bltu` 分开）；
`_wave_check.mjs` 断言 `w_alu_zf` / `w_alu_lt` 只按 funct3[2] 二选一、`taken` 部件
「被点亮 ⟺ 是分支指令」两个方向都成立。

### 1.4 分支的 `alu_op` 一律 `SUB`：有符号 / 无符号分不开

随 1.3 一起修。改之前 `c.alu_op = AluOp::SUB` 对所有分支生效，
所以「有符号比较」与「无符号比较」在 ALU 里没有区别——`bltu` 实际按有符号在比。

**修法**：`rv_control.hpp` 的 `OP_BRANCH`：

```cpp
if (funct3 & 0b100) c.alu_op = (funct3 & 0b010) ? AluOp::SLTU : AluOp::SLT;
else                c.alu_op = AluOp::SUB;
```

### 1.5 反汇编器把 4 类保留编码当合法指令执行

`rv_disasm.cpp` 的 `decode()` 是**执行路径的一部分**——`rv_core.cpp:248` 调它，
`:275` 用 `d.kind == InstrKind::INVALID` 触发陷阱。所以这四处的宽松等于「非法编码照跑」。

| 位置 | 改前 | 改后 | 后果 |
|---|---|---|---|
| `OP_JALR` | 不看 funct3，`jalr` 的 funct3=1..7 全当合法 | 只认 `funct3=000` | 学生拿到一条「能跑但规范没定义」的指令，而不是非法指令异常 |
| `OP_MISC_MEM` | 不看 funct3 | 只认 000(FENCE) / 001(FENCE.I) | FENCE 的保留编码照跑 |
| `OP_OP` | 除 sub/sra 外不看 funct7 | 只认 `0x00`，以及 `0x20` 且 f3∈{0,5} | **RV32M 的 mul/div/rem（funct7=0x01）被静默当成 add/sll/... 执行**：不报错，只是算出一个错值 |
| `OP_OP_IMM` | 移位不看 funct7 | `slli` 要求 `funct7=0x00`；`srli/srai` 只认 `0x00`/`0x20` | 保留编码被当合法 `slli` |

第 3 条尤其要紧：**「不报错的错值」比报错难查得多**。

注意只有移位那两条要看 funct7 —— `addi` / `slti` / … 的「funct7」其实就是立即数的高 7 位，
取值自由，不能一起卡死。这一点在 `rv_disasm.cpp:149-153` 写了注释。

**附带修掉一处文本残缺**：五个 `default:` 分支只置了 `kind` 没置 `mnemonic`，
而紧随其后的 `ostringstream` 块是**无条件执行**的，于是非法指令的 `text` 变成
`" a0, a1, 8"` —— 一条没有指令名的操作数列表。原先用 `text.empty()` 判断是否覆盖，
正好被这个「非空的垃圾文本」绕过。现在统一收口到 `.word 0x…`（`rv_disasm.cpp:289-292`）。

**复验**：`difftest/run.py` 的非法编码语料、`test_sim.py:262-270` 的 7 条非法编码、
`difftest/probe.py` 的 X 节（见 5.3）。

### 1.6 `compile_server.py` 的 gcc 静默回退

**症状**：gcc 存在但编不过时，原先**悄悄改用微型汇编器**。学生写错一条指令，
看到的却是回退器报的另一句话（行号、措辞、指的位置都对不上），
甚至可能被回退器按自己的宽松语法「编成功」跑出另一个程序。

**改前**：

```python
result = _compile_with_gcc(source, out_dir)
if result["success"]: return result
# gcc 失败时静默回退到微型汇编器      ← 删除
```

**改后**：gcc 存在时失败即失败，把 gcc 的报错原文交回去；回退只在 gcc 根本不存在时启用。

**顺带查清的一件事**：本机 `riscv-none-elf-gcc` / `riscv64-unknown-elf-gcc` /
`riscv32-unknown-elf-gcc` / `riscv64-linux-gnu-gcc` / `riscv64-elf-gcc` **全部 NOT FOUND**。
也就是说**产品实际使用的编译器就是 `asm.py`**——`asm.py` 不支持什么，产品就不支持什么。
这条事实决定了第 3 节的定级：那些不是「测试工具的小毛病」，是**产品功能缺口**。

## 2. 前端：11 根线的判据错了或恒亮

恒亮与接反都属于**躲得过「必须包含」型断言**的病，这个项目已经栽过四次
（`csr_we` / `dmem` / `csr` / 现在的 `taken` 一族）。

### 2.1 `taken` 一族（3 根）

| 线 | 改前 | 改后 |
|---|---|---|
| `w_alu_zf` | `active: () => true` —— **恒亮** | `branch && !f3bit(s,2)` |
| `w_alu_lt` | 不存在 | `branch && f3bit(s,2)`（新增） |
| `w_dec_beq` → `w_dec_branch` | 名字与语义不符 | 更名，`decoder.branch_out` |

`w_alu_zf` 恒亮的后果是**拖着 `taken` 单元在每条指令上点亮**——`addi`、`lw`、`jal` 全亮。

### 2.2 PC 目标链（8 根）

| 线 | 改前 | 改后 | 性质 |
|---|---|---|---|
| `w_immadd_m3` | `is_jalr` | `!is_jalr` | **正好接反**：jal 时该亮却灭、jalr 时不该亮却亮 |
| `w_m3_m2` | `is_jalr` | `jumpOrJalr` | 漏判 jal |
| `w_m4_m2` | `branch.taken` | `!jumpOrJalr` | 漏判 jal |
| `w_m2_m1` | `branch.taken \|\| jumpOrJalr(s)` | `pcSel` | 漏了「不跳的分支 pcSel 仍为 1」 |
| `w_add4_m1` | `() => true` | `!pcSel(s)` | 恒亮 |
| `w_add4_m4` | `() => true` | `!(branch && taken)` | 恒亮 |
| `w_immadd_m4` | `branch.taken` | `branch && taken` | 少了 `branch` 这道门 |
| `w_m1_m6` | `() => true` | `!isMret(s)` | 恒亮：mret 时学生看到的 PC 来路是错的 |

### 2.3 点亮契约（`docs/HL_CONTRACT.md`，新增）

改前端点亮规则之前**必须先读契约**——这是本轮差点犯的一个真错误。详见第 8 节。

契约的一句话：**一根线本周期亮 ⟺ 这一拍它真的在传值；一个部件亮 ⟺ 至少有一根相邻的线、
或一个挂在它端口上的网络亮。** 其中 MUX 的判据落在**端口**上：
每个 MUX 只点亮它本周期选中的那一路数据输入，另一路灭，**与下游有没有被用到无关**。
四个 PC-MUX 因此永远恰好亮一路，「互斥」可以直接写成断言。

### 2.4 语法高亮：一个从写下那天起就没生效过的分支

`frontend/src/utils/riscvLang.ts` 的 `token()` 里，助记符分支在前、寄存器分支在后，
而助记符分支对**任何字母开头的词**都会 `return`（不认识就 `return 'variableName'`），
于是下面那条寄存器正则**永远走不到**：`a0` / `sp` / `t0` 全被染成 `variableName`，
「寄存器用 atom 色」这件事从来没生效过。而且那条正则没加 `$` 锚点，
真走到了也会把 `zeros` 当成 `zero` 吃掉。

**修法**：一次取出整词再分类——`MNEMONICS` → `REGISTERS` → `.` 开头的 meta → 兜底。
`REGISTERS` 改为完整表（`x0`~`x31` + 全部 ABI 别名，含 `fp`），并 `export` 出来供对账脚本用。

## 3. `asm.py` 功能补全（这是产品功能，不是测试工具）

19 个实测用例：**改前 OK = 7 / FAIL = 12**。逐条：

| # | 缺口 | 证据 | 学生会看到 |
|---|---|---|---|
| a | 缺 `li`/`mv`/`nop`/`ret`/`call`/`beqz`/`bnez` | 分派表 | `不支持的助记符: li` |
| b | 访存偏移**必须十进制** | 正则 `^(-?\d+)\((\w+)\)$` | `lw t0, 0x10(sp)` → **`'NoneType' object has no attribute 'group'`** |
| c | 标签必须独占一行 | `line.endswith(":")` | `L: addi a0,a0,1` → `KeyError: 'L'` |
| d | `jalr` 只认 `jalr rd, rs1, imm` | 中间操作数走 `reg()` | `jalr ra, 0(ra)` → `unknown register 0(ra)` |
| e | 寄存器别名缺 `fp` | 别名表 | `unknown register fp` |
| f | `reg()` 的 `x` 分支不校验 0–31 | `return int(r[1:])` | `x99` 静默污染编码字段，生成一条谁也没写过的指令 |
| g | 除 `.word` 无数据定义 | 无 | 写不了数据段 |

(b) 尤其糟：**报错完全无法理解**。而且同一个文件里的 `imm()` **是支持** `0x` 的——
于是 `addi a0, x0, 0x10` 能过、`lw t0, 0x10(sp)` 崩，**同一份汇编里两条互相矛盾的规则**。

**修法**（全部集中在入口解析，不动编码核心）：

- `li` 小常数一条 `addi`，否则 `lui` + `addi`，**复用已有的 `%hi`/`%lo` 舍入补偿**
  （`(target + 0x800) >> 12`，已逐位核对正确）；
- 新增 `mem_operand()`：偏移复用 `imm()`，失配时报
  「访存地址写法不对：…（应为 偏移(基址寄存器)，例如 0x10(sp)）」；
- 标签支持行内；
- `jalr` 支持 `jalr rd, imm(rs1)` 与 `jalr rs1`（rd 默认 `ra`），保留三操作数形式；
- 别名表补 `fp`；`reg()` 校验 0–31 并给出可读报错；`_chk()` 校验立即数范围，
  超范围**报错而不是静默掩码**。

**好消息**：编码核心 `enc_r/i/s/b/u/j` 逐位核对**全部符合 RISC-V 规范**
（B 型 `imm[12|10:5]`、J 型 `imm[20|10:1|11|19:12]` 位分布都对），**本轮一行未改**。
缺陷全在入口解析，所以改动风险低。

**复验**：
- `backend/test/test_asm.py`（新增）—— 55 条断言，把上述每条缺口写成用例，
  比的是「编码器算出来的 == 我手算的字面量」；
- `backend/test/test_pseudo.s`（新增）+ `test_sim.py` 的测试 4 —— 端到端，
  验的是「CPU 执行后的结果」。两份互补：`test_asm.py` 两边可能一起错，
  端到端那份不会。

### 3.1 前端关键字表与 `asm.py` 逐条对齐

`riscvLang.ts` 的 `MNEMONICS` 与 `asm.py` 的能力长期双向不一致：
前端高亮 `nop`/`mv`/`li`/`ret`/`call` 而后端一个都不支持；后端支持 `mret` 而前端不高亮
（`mret` 恰是本项目最大增量——中断/异常——的返回指令）。

**人话**：学生写 `li a0, 10`，编辑器标成合法关键字（和 `addi` 同色），
点「编译」才报「不支持的助记符: li」。而 `li` / `mv` 恰是教材里最常出现的两条。

**修法**：先补 `asm.py` 的能力（上一小节），再把前端表改成与之一致，并新增
`tools/_lang_check.mjs` **双向对账**——它不重抄任何一张表，而是**直接问 `asm.py` 能不能编**，
再跟 `MNEMONICS` 比。改一边漏了另一边就会报错。已挂进 `check_all.py` 默认流程。

## 4. 验证体系：从「断言自证」到独立判据

这是本轮**根因层**的改动。上面 6 个 bug 能长期潜伏，共同原因是同一句话：
**错误实现 + 恒真断言可以长期共存**（AUIPC 是标本，`dmem`/`csr`/`taken` 三次恒亮是同一形态）。

### 4.1 自写独立参照模型 + 差分测试（`backend/test/difftest/`）

新增 7 个文件。独立性靠一条**硬约束**：编写 `refmodel.py` 时只依据 RISC-V Unprivileged ISA
规范 + 官方 opcode 表，**禁止阅读** `rv_core.cpp` / `rv_control.hpp` / `rv_immgen.hpp` /
`rv_alu.hpp` / `rv_disasm.cpp`，并在文件头写下这条声明。做不到这条，价值打对折。

| 文件 | 作用 |
|---|---|
| `refmodel.py` | 零依赖的 RV32I 参照模型（约 34 KB） |
| `enc.py` | 纯编码语料生成器（**不 import `asm.py`**）——因为 `asm.py` 表达不了非法编码 / 保留 funct7 / 非对齐 / 越界 / 任意 CSR 数字地址，而这些恰是最易错的角落 |
| `corpus.py` | 语料：初态靠 prologue 指令流构造（后端只有 `load_elf`，没有「设寄存器」命令），参照模型从同一 PC、同一全零内存执行完全相同的指令流，顺带把 prologue 也纳入覆盖 |
| `run.py` | 锁步比对，**55 个用例，55/55 通过**；退出码 0=全过 / 1=失配 / 2=基础设施错 |
| `sim.py` | 后端子进程封装 |
| `probe.py` | 定向探针 + 全组合解码扫描（见 4.3） |
| `roundtrip.py` | 汇编↔反汇编往返（见 4.2） |

**比什么**：`pc` / `instruction` / `next_pc` / `instruction_fields` / `immediate` /
`control_signals` / `reg_reads` / `regfile[32]` / `alu.op1,op2,result` / `memory.*` /
`branch.*` / `writeback.*` / `csr`（白名单）。
**排除**：`csr.mtime`（= 周期数）、`csr.mtimecmp`（自定义 CSR `0x780`）、
`disassembly`（文本格式属实现自由度）。

**两个必须记住的坑**（都写进了代码注释）：

1. ⚠️ **必须用 `step`，绝不能用 `get_state`** —— `main.cpp:202` 的 `get_state` 内部会真的
   调 `core.step()`，在循环里用它会每周期多执行一条。
2. ⚠️ **`json.dumps(..., ensure_ascii=False)` 是硬要求** —— C++ 侧极简 JSON 解析器不认 `\uXXXX`。

**停机语义鸿沟**的处理：**不**让参照模型复刻「`ecall` + `mtvec==0` ⇒ halted」这条项目自定义
语义，改为语料里显式声明停机点，停机那一周期单独断言「后端确实在此周期置 halted」；
`mtvec != 0` 的用例照常跑到底（能进 handler、`mret` 回来），从而全周期逐字段可比。

### 4.2 汇编器 ↔ 反汇编器往返（`roundtrip.py`）

**判据**：`源码 --asm.assemble--> W --C++ 反汇编--> 文本 T --归一化--> 源码' --assemble--> W'`，
断言 `W' == W` —— **比的是机器码逐字相等，不是文本相等**。
文本格式属于实现自由度（`run.py` 的 `SKIP_KEYS` 也排除了 `disassembly`），
所以「文本长得不一样」不算失败，「文本换不回同一串机器码」才算。
这条判据**不依赖任何外部参照**，两份实现互相验，就能抓出「编码位拼错」「译码位读错」
「同一个 funct3 编进 A 却解成 B」这一类错误。

**结果：9/9 组通过**。语料 9 组：R 型 / I 型 / 访存 / 分支 / 跳转 / U 型 / 伪指令 /
系统与 CSR / 非法编码。

**两处归一化（是表达口径差异，不是错误）**：

1. U 型立即数：反汇编打印的是符号扩展后的 32 位值（`lui t0, -2147483648`），
   而 `asm.py` 收 20 位立即数（`0x80000`）——`v >> 12` 即可互转；
2. 分支 / jal 的落点：反汇编打印相对偏移，`asm.py` 只收标签——测试在目标地址处合成
   标签 `L%08x`。

**`--raw` 模式给出这两处之外的原始证据**：关掉归一化后 **57 条能 / 74 条不能**直接回汇，
74 条全部来自上述两类。这是用来证明归一化确实只堵了这两处、而不是把失败掩盖过去的。

**变异自检**（防「断言自证」）：把 R 型组第 8 条 `sra s7, s8, s9` 的 rs2 改一位
（`s9(x25)` → `s8(x24)`），往返**必须精确报出这一条**而不是整组。三点一次验完：
① 比较逻辑是活的；② 能精确到某一条；③ 能抓到寄存器字段级别的差异。
结果：`变异被精确捕获（第 7 条 sra 的 rs2 改一位）`。

**已知能力边界**（诚实标注，以免误读成通过）：`fence` / `fence.i` 两侧都不支持
（`asm.py` 没有这两个助记符，前端高亮表同样没有），只能写 `.word`；
反汇编器把 funct3=000 与 001 都渲染成 `fence`，这一位信息在文本上不可逆——
既然两侧都不支持，往返本来就走不通，故不列入语料，只在此备案。

### 4.3 非法编码全组合扫描（`probe.py` 的 X 节）

**252 个组合**（opcode × funct3 × funct7），其中 **121 个取陷阱（全部 mcause=2）**。

对每个组合做两件事：

1. **守门**：`write_bin([word])` → `sim.load` → 断言 `st["instruction"] == "0x%08x" % word`。
   这是在检查「反复 load 是否真复位」这个前提本身——前提不成立的话，整张表都是假的。
2. 与 `RefModel([word]).step()` 比 `instruction_fields` / `immediate` / `control_signals` 三项。

**结果：四项（含合法性判断）在全部 252 个组合上一致，包括非法组合。**
即 [C]12「**呈现不设合法性闸门**」成立：非法与否的唯一后果是取陷阱、不提交。

**独立性诚实标注**（这句话必须留着）：这张合法性表是直接读后端得来的（参照模型没参与），
但「四项在非法组合上长什么样」的规则本就源于同一批实测，那次比对只能**防漂移**，
不构成对后端的独立验证——独立验证靠 `run.py` 的语料。

### 4.4 波次顺序断言补全（`tools/_wave_check.mjs`）

**补之前**：只有 7 对写死的模块对 + 1 条条件式。
**整条 ALU 操作数选择链、写回链、PC 链的内部次序无任何检查。**

**补的过程里翻了一次车，值得记下来**：

第一版我写了一条「线级」不变量：*X 的汇端口就是 Y 的源端口 ⟹ X 早于 Y*。
跑出来 **0 处失败**，看着挺漂亮。但加上「比过多少对」的计数后发现——**比过 0 对**。
原因是 wire 的 `to` 是**模块的输入端口**、下一段线的 `from` 是同一模块的**输出端口**，
中间隔着模块本身，端口名不可能首尾相接。**这条断言从头到尾是空转的，却一路显示全过。**

这正是本项目反复出现的病（实现错 + 断言恒真），只不过这次病在断言自己身上。

**改对后的形式**（问的是「信号有没有逐级往下走」，不问「哪个部件先亮」）：

> ★ 若载波 X 落到模块 M 的某个（非时钟沿写）端口上，载波 Y 从 M 出去，
> 则 `frame(X) < frame(Y)`。

「载波」= 一根线，或一条网络引线（`NET_LINK` 里那些没画成 wire 的真实连接），
两者在波次模型里是同一回事。覆盖的三条链（写进代码当文档 `CHAIN_DOC`）：

```
ALU 操作数：w_rf_ma0 → w_muxa0_muxa → w_ma_alu；w_rf_mb1 → w_mb_alu
写回：      w_alu_wb0 → w_wb0_wb → w_wb1_wb → w_wb_rf（→ 落在 regfile.wdata 上）
PC：        w_alu_jalr → w_jalr_m3 → w_m3_m2 → w_m2_m1 → w_m1_m6 → w_m6_m5 → w_m5_pc
```

**为什么只能这么写**（这一段踩过坑，写清楚免得下次又写错）：

- 模块帧只在**连接那两级的线本周期亮着**时才有顺序关系——线不亮就不建边。
  实测反例：`csrrw` 那拍 `wbmux0=7` 而 `wbmux1=4`，因为 `wbmux1` 的 sel 是 `is_csr=1`，
  选中的是注解网络 `csr_old`，`w_wb0_wb` 那根线灭了，两级之间没有边。
- 模块级写 `['pcmux5','PC']` 或 `['wbmux','regfile']` 更是错的期望：PC 的帧来自它自己
  （`pc_next` 是时钟沿切开的幻影节点 `#in`，不进模块帧），regfile 的帧来自读口——
  这两个模块本来就在第 0~2 波就亮了，「早就在被读」。**写回 / PC 更新发生在最后，
  这件事模块帧表达不了**，只有线级帧说得清（这也正是写回链最后一跳
  `w_wb1_wb < w_wb_rf` 的价值所在）。

**这不是独立验证，是回归护栏**（诚实标注，写在代码注释里）：这条不变量对当前的分层算法是
**结构性成立**的（最长路径分层保证每条边两端深度至少差 1），所以它抓不到
「分层算法想错了」，只能抓「分层被改坏」。

**证明它真会响**（两步，都不是纸上推演）：

1. **变异自检**：对 `CHAIN_DOC` 三条链的**每一跳、每个周期**，只要两根载波这一拍都亮着，
   就把上游的帧强行抬到与下游相等，要求被精确报出来。
   结果：`CHAIN_DOC 三条链共 62 处跳变，逐处变异全部被捕获`（`_hl_states.jsonl`）。
   同时加了静态自检：`CHAIN_DOC` 里的线必须存在、相邻两跳必须真的接得上、
   `SINK_PORTS` 里每个端口必须存在且没有连线从它出发——防「改名后链条变成纸面文档」。
2. **实弹射击**：临时把 `datapathWave.ts` 的 `frameOfWire` 改成取汇点深度（模拟「分层被改坏」），
   跑出来 **8 处失败、退出码 1**，然后改回。
   ``` 
   ✗ 第 6 周期（csrrw）顺序不对：decoder：进来的 w_imem_dec=2 不早于出去的 csr_addr=2
   ```

**四个夹具的实测数据**：

| 夹具 | 周期数 | 比过的载波对 |
|---|---|---|
| `_hl_states.jsonl` | 10 | 298 |
| `_hl_ecall_states.jsonl` | 7 | 210 |
| `_csr_states.jsonl` | 13 | 384 |
| `_hl_branch_states.jsonl` | 28 | 875 |

### 4.5 MUX 互斥断言（`_hl_check.mjs` + `_wave_check.mjs`）

这是补之前**零覆盖、教学上最致命**的一类错：把一个 MUX 的两条输入写反
（`w_immadd_m3` 原先就是接反的），只看「亮了什么」永远发现不了。

期望值**直接从 `control_signals` / `branch` 算，不 import 前端那几个派生函数**——
否则就是拿被测实现去验证被测实现。

```
muxa0  → w_rf_ma0 ‖ w_imm_muxa0   由 !is_lui 选
muxb   → w_rf_mb1 ‖ w_imm_muxb    由 !alu_src 选
wbmux0 → w_alu_wb0 ‖ w_dmem_wb0   由 !mem_to_reg 选
pcmux1 → w_m2_m1 ‖ w_add4_m1      由 branch‖jump‖is_jalr 选
pcmux2 → w_m3_m2 ‖ w_m4_m2        由 jump‖is_jalr 选
pcmux3 → w_jalr_m3 ‖ w_immadd_m3  由 is_jalr 选
pcmux4 → w_immadd_m4 ‖ w_add4_m4  由 branch&&taken 选
```

`_hl_check.mjs` 的 `EXPECT` 同时从「必须包含」升为三元组 `{dis, must, mustNot}`，
并加了模块级双向断言（照抄 `_wave_check.mjs` 的 dmem 模式）。
**反向断言是唯一能抓「本该亮却没亮」的手段**——`csr_we` 长期没亮而无人发现的病根就在这里。
现有 19 条断言条目；脚本统计每条被夹具命中的次数（`_hl_check.mjs:135,162`），
**命中 0 次的条目判失败**——否则一条从没被任何夹具走到的断言会永远显示通过。

### 4.6 `tools/check_all.py`：把「漏跑的断言」绑成一条链

**为什么需要它**：断言散在好几个独立脚本里，得有人记得挨个跑。
`_csr_test.s` 的状态流（`tools/out/_csr_states.jsonl`）**早就生成过**，
但两个 check 脚本缺省只吃 `_hl_states.jsonl`，于是
**`_wave_check.mjs` 里那几条 CSR 反向断言长期等于没跑**——脚本是绿的，因为它压根没看那个文件。

`check_all.py` 把「生成状态流 + 逐个校验」串成一条链，谁漏跑都会露出来：
生成 4 份状态流 → 悬空端口扫描 → 几何自检 → 场景树渲染 → `_hl_check.mjs` ×4 →
`_wave_check.mjs` ×4 → 语法高亮表对账。**源码树里 16 步全部通过。**

> 在**交付包**里跑会看到 1 步「跳过」而不是「通过」——包里没有 `frontend/node_modules`，
> 最后那步读不到 `riscvLang.ts`。跳过不算通过，理由和修法见 §10。

`启动-Windows.bat:11` 的逻辑是「有 exe 就跳过编译」，所以 **Windows 学生会直接跑到这个旧核心**，
AUIPC 算错、`taken` 还是那张只认 BEQ 的 switch、非法编码照跑。

**根因**：打包用的是 `git archive HEAD`，而 `rv32i_sim.exe` 在 `.gitignore` 里、根本不在
git 里；当时的补救是「手工从 build 目录补一个进去」，补的是**编到一半的产物**，没跟着源码走。
这类「构建产物不进版本库、只能人工补」的流程本身就会重犯——所以下面第 4 条把它写成了断言。

### 本次顺带修掉的一个包内缺陷

`tools/check_all.py` 在交付包里必然报「失败 1 步」——`_lang_check.mjs` 静态 import 了
`riscvLang.ts`，而后者依赖 `@codemirror/language`，该依赖在包里被**故意排除**。
报错是 `ERR_MODULE_NOT_FOUND` 的一大段堆栈，把「环境没装」误报成「断言失败」。

修法：`_lang_check.mjs` 改成动态 import，缺依赖时明说原因并以**退出码 3（跳过）**退出；
`check_all.py` 认得这个码，显示 `[跳过]` 并在结尾单列——**跳过不算通过**，
免得「没跑」被当成「跑过了」。源码树里依赖齐全，仍是 16/16 全过。

## 11. 一句话复盘

这一轮真正修的不是 6 个 bug，而是**「怎么知道自己是错的」**这套机制：
AUIPC 证明了「后端错、前端忠实镜像、断言全绿」可以长期共存，
所以本轮补的三样东西——自写参照模型、汇编↔反汇编往返、无法编码组合全扫描——
都不是「多几条断言」，而是**三类互相独立的判据**。
D5 那一次「比过 0 对却显示全过」也说明：**断言自己也需要被验**，
所以每引入一条新断言，都配一个变异自检。
